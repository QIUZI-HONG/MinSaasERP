## 二、测试范围与亮点结论

### 功能正确性（接口层 48/48 ✅）
- 鉴权：登录/注册 正反向 15 用例全过（含空值、重复、token 篡改、过期）
- 商品/客户 CRUD：含搜索、唯一约束、外键保护（被引用不可删）
- 订单：**事务扣库存、取消回补、金额防篡改**（客户端伪造金额不生效）、明细总额一致性
- 看板：统计口径正确（**已取消订单不计入营收**，实测验证）

### 并发一致性（6/6 ✅，本项目最强项）
- **超卖防护**：10 个并发请求抢购仅 5 件库存的商品 → 恰好成功 5、拒绝 5、0 服务器错误，库存不超卖（事务生效）
- **订单号唯一**：15 并发下单全部唯一
- **库存一致性**：下单-取消循环 5 轮后库存精确回补 100/100

### 安全结论
- ✅ SQL 注入（OR/注释/万能密码）全部拦截，数据库无损
- ✅ JWT 篡改载荷/错误密钥/过期 token 全部 401
- ✅ 密码 bcrypt 哈希存储（直查数据库验证），登录失败响应不泄露用户是否存在
- ✅ 存储型 XSS 载体可入库（API 不编码属正常），**前端渲染为文本未执行**（U7 实测 Chrome 验证）
- ⚠️ 内部错误不泄露堆栈（500 统一友好提示）

### UI 全流程（Chrome 实测，20/21 ✅）
登录 → 看板（统计与后端一致）→ 商品增删改查/搜索 → 客户管理 → **新建订单（两行明细）→ 金额精确 727 = 299×2+129 → 明细展开 → 状态流转 → 取消** → 刷新保持登录 → 退出后路由守卫生效。14 张过程截图见 `tests/report/screenshots/`。

## 三、缺陷清单（按严重度分级）

### 🔴 P1 严重（2 项）

| # | 缺陷 | 复现 | 影响 |
| --- | --- | --- | --- |
| 1 | **可创建负价商品** | `POST /products` 传 `price: -50` 返回 200 | 负价商品下单导致订单金额为负，营收统计被污染，存在刷单/套利风险 |
| 2 | **登录失败无错误提示**（UI） | 错误密码登录 → axios 401 拦截器误触发 `location.href='/login'` 整页刷新 | 错误提示被刷新冲掉，用户只看到页面闪一下，无任何反馈；拦截器应将登录接口 401 排除在"会话过期"处理之外 |

### 🟠 P2 中等（4 项）

| # | 缺陷 | 复现 | 影响 |
| --- | --- | --- | --- |
| 3 | **畸形 JSON 请求体 → 500** | `POST /auth/login` body=`null` | body-parser 4xx 错误被全局错误处理器吞成 500，应返回 400 |
| 4 | **超大请求体 → 500** | 200KB body（默认限制 100KB） | 应返回 413，实际 500 |
| 5 | **删除不存在资源 → 500** | `DELETE /products/99999`、`DELETE /customers/99999` | 资源不存在应 404，实际 500（Prisma P2025 未处理） |
| 6 | **价格传非数字 → 500** | `price: "abc"` | `Number("abc")=NaN` 写入失败，应 400 参数校验 |

### 🟡 P3 建议（9 项）

| # | 建议 | 说明 |
| --- | --- | --- |
| 7 | 订单状态机校验流转顺序 | 当前 PENDING→DONE 跳级被接受，建议按 `STATUS_FLOW` 限制 |
| 8 | 登录失败限流/锁定 | 连续 6 次错误密码无任何限制 |
| 9 | 关闭 `X-Powered-By: Express` | 暴露技术栈信息（`app.disable('x-powered-by')`） |
| 10 | CORS 收敛白名单 | 当前 `Access-Control-Allow-Origin: *`，生产应收敛 |
| 11 | 数值/布尔类型严格校验 | `quantity: true` 被 `Number()` 转 1 接受，建议用 zod 等做入参校验 |
| 12 | 字段长度上限 | 用户名 1000 字符、商品名 2000 字符均可入库 |
| 13 | 价格为 0 的业务校验 | 0 元商品被接受，建议业务层禁止 |
| 14 | API 幂等键 | 相同请求连发两次创建两单，目前仅靠前端按钮 loading 防重 |
| 15 | `orderNo` 生成方式 | 当前 `Date.now()`，高并发下理论上可能撞号（本次 15 并发实测未撞，建议改雪花 ID/序列） |

## 五、结论

1. **核心业务链路质量高**：97.9% 整体通过率，事务一致性（扣库存/回补/防超卖）是最大亮点，达到可演示、可讲解的交付水平
2. **2 个 P1 缺陷建议修复后交付**：#1 负价商品（加 `price > 0` 校验即可）、#2 登录拦截器（排除 `/auth/login` 接口即可），均为小改动
3. P2 缺陷集中在一个根因：**全局错误处理器未区分 HTTP 状态错误与内部错误**，加一个 body-parser 错误处理中间件可一次性解决 #3/#4，另补 P2025 → 404 与入参类型校验
4. P3 为生产化建议，不影响演示与面试，可按优先级渐进完善

> 备注：测试产生的脏数据（测试商品/订单）已清理，数据库已恢复干净种子基线（见测试脚本同目录说明）。
